# Spec Axis Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a thirteenth reviewer, `spec`, that measures the diff against the originating issue or spec document, reported as a separate axis that is never merged with code findings.

**Architecture:** A normal reviewer (rubric + agent body, same pattern as the other twelve) whose one novelty lives in triage: triage resolves the spec, emits `spec_source`, and dispatches `spec` only if resolution succeeded. Synthesis keeps the two axes in separate pools, never dedups across them, and excludes spec findings from the out-of-diff tripwire.

**Tech Stack:** Markdown skills and agent bodies (no runtime code), bash validator (`scripts/validate.sh`, bash 3.2 compatible), bash validator tests (`scripts/validate.test.sh`), vitest for the CLI.

**Spec:** [`docs/superpowers/specs/2026-08-20-spec-axis-design.md`](../specs/2026-08-20-spec-axis-design.md)

**Revision note.** This plan was rewritten after review-pro reviewed its own first draft. Six of that draft's instructions were wrong, not merely thin: the prescribed test cases called four helpers that do not exist, their `sed` mutations matched zero bytes of the fixture so both cases would have passed while measuring nothing, the single flagged risk warned about a breakage that cannot occur, four files that need editing were absent from the Modify list, one step ordered a verbatim copy that the Global Constraints forbid, and Task 1 shipped a roster entry ahead of its producer. Every bash snippet below has now been executed against a sandbox copy of `scripts/` and its output observed. Where a step claims a command fails, that failure was seen.

## Global Constraints

- **No em dash (`—`), `·`, `→`, curly quotes, or `…`** in any file this plan writes. Restructure sentences instead of substituting `-`. Verify with `grep -c "—" <file>` returning 0. Where an existing file's line must be echoed, reproduce the load-bearing **strings**, not the bytes: the twelve sibling agent bodies contain an em dash in their schema tail, and `scripts/validate.sh` greps only for `evidence_refs` and `same evidence bar`, so those two substrings are what parity requires.
- **Severity ladder is fixed** (`core/shared/severity.md`): BLOCK on any Critical or High, REQUEST CHANGES on any Medium or above, APPROVE on Low/Nitpick only. Do not add levels.
- **`scope-creep` findings cap at Medium.** This is what makes scope creep unable to block. Never emit Critical or High for that class. Note the cap does not make the class free: one Medium still turns APPROVE into REQUEST CHANGES.
- **Reviewer rubrics require these nine sections, matched exactly and anchored** (enforced by `scripts/validate.sh`): `## Role & mandate`, `## Scope`, `## What this reviewer flags`, `## Evidence & severity`, `## No unresearched findings`, `## Approval bar`, `## Output schema`, `## Cross-reviewer handoff`, `## Tone`. `##` not `###`.
- **Agent bodies embed the output schema inline.** Subagents do not load `core/shared/`, so the schema must travel in the body.
- **bash 3.2 (macOS default).** `"${arr[@]}"` on an empty array trips `set -u`. Use newline-delimited strings and `while IFS= read -r` loops.
- **New test cases go BEFORE the summary block** in `scripts/validate.test.sh`, never appended after it. Appending leaves the printed count wrong (observed: five new cases appended after the summary produced `pass=12` when seventeen had run). The `EXIT` trap added in #28 keeps the exit status correct either way, but the summary is what a human reads.
- **Case letters H, I, and J are already used** in `scripts/validate.test.sh`, H and I twice each. New cases start at K.
- **Every task ends green:** `./scripts/validate.sh` prints `OK: all artifacts valid`, `bash scripts/validate.test.sh` ends `fail=0` **and exits 0**, and `cd cli && npx vitest run` passes.

- [ ] **Step 6: Add the resolution step to the triage skill**

Insert as a new step between the current 5 and 6, renumbering what follows:

```markdown
6. **Resolve the spec.** Find what the change was supposed to do, trying these in order and falling through on any failure:
   1. An **explicit argument** passed to the review (a file path, or an issue URL). An explicit instruction always wins; if the user named a spec, do not go looking for a different one.
   2. The **PR body and issue references in commit messages** (`#123`, `Closes #45`), via `gh pr view` and `gh issue view`.
   3. A **file** under `docs/`, `specs/`, or `.scratch/`. Match the branch's last path segment as a substring of the filename, ignoring any leading date prefix: branch `feat/spec-axis` matches `docs/superpowers/specs/2026-08-20-spec-axis-design.md`.    4. **Nothing.**

   Every link falls through silently to the next. `gh` missing, `gh` not authenticated, the repo not hosted on GitHub, and the branch not being a PR are all ordinary conditions, not errors. Use every reference you find rather than choosing between them: the intent of a change closing three issues is the sum of the three.

   Emit `spec_source` recording what you found, not merely whether you found something. Stage 3 prints it verbatim, because a reader who cannot see what the review was measured against cannot judge a spec finding.

   **Dispatch `spec` if and only if `spec_source.kind` is not `none`.** This is the one dispatch decision that does not come from the signal map, because spec relevance has nothing to do with which files changed. The "when in doubt, dispatch" default does **not** apply here: dispatching a spec reviewer with no spec is a guaranteed waste, not a possible finding.
```

- [ ] **Step 4: Add the Spec axis section**

Insert immediately after `## Out-of-diff evidence check`:

```markdown
## Spec axis

Spec findings arrive in the same stream as code findings and are kept apart from them from here on.

- **Partition before dedup.** Two pools, code and spec. Dedup runs within each pool and never across. A spec finding and a code finding on the same line are different claims: "this should not exist" is not "this has a bug", and merging them loses both.
- **The verdict is the worse of the two axes, and its label names the driver:** `## Verdict: BLOCK (code)`, `REQUEST CHANGES (spec)`, `BLOCK (code + spec)`. The severity ladder is unchanged, so a `spec.scope-creep` finding capped at Medium requests changes and never blocks.
- **Absence is always stated.** If `spec_source.kind` is `none`, write one line: `Spec: skipped, no spec found.` If the axis ran and found nothing, say so: `Spec: no mismatch against <ref>.` Silence is not an acceptable output for this axis in either case.
- **Print `spec_source` verbatim** under the verdict, so the reader can see what the review was measured against.
- **Never re-rank a spec finding against a code finding.** Reporting them separately is what stops one axis from masking the other.
```
