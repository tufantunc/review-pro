## Correctness findings: none

I found nothing to flag in the added or changed code. What I checked in the working tree:

- **The env var is real and `aspire run` reads it.** `ASPIRE_CLI_START_TIMEOUT` is defined at `src/Aspire.Cli/CliConfigNames.cs:10`. `aspire run` parses it at `src/Aspire.Cli/Commands/RunCommand.cs:182` through `src/Aspire.Cli/Commands/AppHostStartupTimeout.cs`, which expects a positive integer number of seconds, so `180` is accepted. The default is `WaitCommand.DefaultTimeoutSeconds = 120` (`src/Aspire.Cli/Commands/WaitCommand.cs:31`).
- **The 120s budget does cover the build.** The timeout starts before `project.RunAsync` and applies to waiting on the build (`RunCommand.cs:296-318`). So the PR's reasoning holds: a cold restore plus build under `aspire run` uses up the 120s default.
- **The shell prefix works.** `VAR=value aspire run` puts the variable into the CLI's environment only. The existing `aspire start` helper already uses the same pattern (`CliE2EAutomatorHelpers.cs:776`). `System.Globalization` is already imported in the helper file.
- **Timeouts are ordered correctly.** Every changed wait now lasts 240s (180 + 60). That is longer than the 180s CLI budget in `SmokeTests` and `DotnetToolSmokeTests`, so the CLI's own timeout message appears before the terminal wait gives up. The polyglot wait goes from 3 to 4 minutes, which is harmless.
- **`BundleSmokeTests` get the longer wait but not the env var.** Those tests launch with `dotnet run`, which builds first and then runs `aspire run --no-build` (`src/Aspire.Hosting.AppHost/build/Aspire.Hosting.AppHost.in.targets:310-318`). The build happens outside the CLI's timer, so the 120s default there covers only startup. The longer terminal wait is appropriate because it now also has to cover the build.
- **Older CLIs should be unaffected.** Support for the variable arrived in #16686 (commit 853656a57). Older published CLIs, which `DotnetToolSmokeTests` may install, would see it as an unknown config key with no effect. That matches the diff comment. I confirmed only that the support commit exists; I did not check older CLI versions.

One gap outside the diff: six other raw `aspire run` calls in the E2E suite still wait up to 3 minutes while the CLI stops at 120s. They are `JsReactTemplateTests.cs:37`, `JavaPolyglotTests.cs:71`, `TypeScriptPolyglotTests.cs:139` and `:451`, `ConfigHealingTests.cs:70`, and `LocalConfigMigrationTests.cs:84`. They can hit the same flake, but they are unchanged and the PR is limited to the smoke tests, so I did not file a finding.
